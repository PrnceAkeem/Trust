# Contributing to Trust

Thank you for helping build Trust thoughtfully. The project is in discovery, so
research quality and clear problem definitions matter as much as implementation.

## Before Contributing

- Read the project brief, roadmap, and relevant research.
- Search existing issues before opening a new one.
- Do not disclose suspected vulnerabilities in public issues or discussions.
- Keep proposals aligned with professional, on-premises IT operations.
- Separate observed facts, assumptions, and proposed decisions.

## Ways To Contribute

- Correct or strengthen research with primary sources.
- Document a real IT operations workflow or failure mode.
- Propose product requirements and measurable acceptance criteria.
- Review threat assumptions and privacy implications.
- Improve documentation and accessibility.
- Implement an approved issue once development begins.

## Issues

Use the provided issue forms. A useful issue explains the operational problem,
the environment, expected behavior, and why the outcome matters. Feature ideas
should describe the need before prescribing an implementation.

Use GitHub Discussions for open-ended questions once Discussions is enabled.
Use Issues for scoped, actionable work.

## Architecture Decisions

Changes that affect security boundaries, protocols, data models, deployment,
storage, compatibility, or public APIs require an Architecture Decision Record
(ADR). Copy `docs/decisions/0000-template.md`, assign the next number, and keep
the status as `Proposed` until accepted.

## Pull Requests

- Keep each pull request focused on one coherent change.
- Link the relevant issue or ADR.
- Explain user-visible and security effects.
- Add or update tests when behavior changes.
- Update documentation with the implementation.
- Avoid unrelated formatting and refactoring.
- Confirm that no credentials, private hostnames, addresses, logs, or user data
  are included.

Maintainers may request that a large pull request be divided into smaller ones.
Approval does not transfer copyright ownership. By submitting a contribution,
you agree that it may be distributed under the Apache License 2.0.

## Research Standards

Prefer primary sources such as official documentation, standards, source code,
release notes, and security advisories. Record access dates for information that
changes frequently. Avoid unsupported superlatives and clearly label inference.

## Community

Participation is governed by [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). By
contributing, you agree to follow it.
