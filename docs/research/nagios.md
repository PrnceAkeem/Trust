# Nagios Core Research Report

## Architecture Summary

Nagios Core's core process is a single scheduling/event daemon that reads a static object configuration at startup, builds an internal execution schedule, and dispatches checks at configured intervals. Checks come in two flavors:

- **Active checks**: initiated by the Nagios daemon itself. A check runs at intervals equal to `check_interval` when the host/service is in a stable "HARD" state, or `retry_interval` when in a transitional "SOFT" state (a state change being confirmed before it triggers a notification) ([Nagios Core Docs – Active Checks](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/activechecks.html)).
- **Passive checks**: results are generated externally (a remote agent, an NSCA submission, a custom script) and written into Nagios's external command file, which Nagios periodically reads and enqueues ([Nagios Core Docs – Passive Checks](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/passivechecks.html)).

Regardless of origin, all results funnel into the same queue and are processed identically by a periodic "check result reaper" event — this is what lets passive results from arbitrary external systems integrate seamlessly with actively-scheduled ones ([Nagios Core – Passive Checks KB](https://support.nagios.com/kb/article/nagios-core-passive-checks-367.html)).

**Remote/passive execution mechanisms:**
- **NRPE (Nagios Remote Plugin Executor)** lets a central Nagios server trigger plugin execution *on* a remote Linux/Unix host: a daemon on the monitored host listens on a TCP port and executes locally-defined commands on request, returning the plugin's exit code/output to the poller — effectively making a remote target actively pollable without SSH.
- **NSCA (Nagios Service Check Acceptor)** is the inverse: a daemon on the central server accepts unsolicited check results pushed by a `send_nsca` client on remote hosts. Packets can optionally be encrypted, and a shared password must match between client and daemon config ([NSCA GitHub](https://github.com/NagiosEnterprises/nsca), [Packt – Passive Checks and NSCA](https://www.packtpub.com/en-us/learning/how-to-tutorials/article-passive-checks-nsca-nagios-service-check-acceptor)).

**Plugin API:** Nagios itself contains no monitoring logic — every check is an external executable (shell script, compiled binary, Python script, etc.) invoked as a subprocess. The contract is minimal: print at least one line of text to STDOUT and exit with one of four codes — 0 (OK), 1 (WARNING), 2 (CRITICAL), 3 (UNKNOWN). Output follows a `TEXT OUTPUT | OPTIONAL PERFDATA` convention: text left of the pipe becomes the human-readable status ($SERVICEOUTPUT$), text right of it becomes machine-parseable performance data ($SERVICEPERFDATA$) for graphing addons. Only the first 4KB of output is read, guarding against runaway plugins flooding the core ([Nagios Core Plugin API docs](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/pluginapi.html), [Nagios Plugin Development Guidelines](https://nagios-plugins.org/doc/guidelines.html)).

**Object configuration model:** Everything monitorable is declared as a typed "object" — Hosts, Services, Host Groups, Service Groups, Contacts, Contact Groups, Commands, Time Periods, Escalations, Dependencies — defined in plain text files/directories referenced via `cfg_file`/`cfg_dir` directives. Objects support single or multiple template inheritance (an object can `use` one or more templates, which can themselves inherit from other templates), Nagios's primary mechanism for avoiding config duplication across large fleets. Host-level custom variables are inherited down into associated service definitions if not explicitly overridden ([Nagios Core Docs – Object Configuration Overview](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/configobject.html), [Object Inheritance With Templates](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/objectinheritance.html)).

## Extensibility Model

The plugin architecture is widely regarded as Nagios's most enduring design win: because the interface between core and check is just "process exit code + stdout text," literally *any* language or existing tool can be wrapped into a check with a few lines of glue code. This produced a large ecosystem (Nagios Exchange) of community plugins for nearly every device, database, and API imaginable, and decoupled the monitoring engine's release cycle from the plugins' — you never patch Nagios core to add a new check type. It's often cited as the reason Nagios became the de facto monitoring standard for two decades despite its rough edges.

Where it breaks down at scale: everything is a text string plus an integer, with no native concept of typed metrics/time series, so trending/graphing requires bolt-on addons (PNP4Nagios, Graphite exporters) parsing the loosely-specified perfdata string; every check is a fork/exec of an external binary, which at high host/service counts becomes CPU- and I/O-heavy on the single central scheduler (a root cause of Nagios's scaling ceiling, see below); plugins have no dependency/versioning management — just scripts dropped in a directory with no sandboxing, signing, or permission model beyond filesystem permissions; and discovery is entirely manual, since the plugin model says nothing about *finding* what to check — every host/service/plugin combination must be hand-declared as a config object.

## Configuration Model

Configuration is done via flat, hand-edited text files organized around the object/template system above. This is powerful (arbitrary inheritance graphs, custom variables, macros) but has a well-documented reputation for being tedious and error-prone at scale:
- No built-in host/service auto-discovery — every monitored entity must be manually declared as an object, then re-declared or updated as infrastructure changes ([softlogicsys.in – Nagios limitations](https://www.softlogicsys.in/top-7-nagios-core-limitations-and-solutions/)).
- No native web-based config UI; the stock web interface is read-only status/reporting, not a configuration tool. To get GUI-based configuration, most shops install the third-party **NConf** addon, a separate PHP application that generates Nagios config files but isn't part of Core itself ([NConf – Nagios Exchange](https://exchange.nagios.org/directory/addons/configuration/nconf/details/), [Nconf on Wikipedia](https://en.wikipedia.org/wiki/Nconf)).
- Config duplication between server-side object definitions and client-side NRPE command definitions is a frequently cited pain point — the same check logic effectively has to be described in two places.
- Major-version upgrades (e.g., 3 → 4) have historically required manual config auditing: parameters were deprecated (`enable_embedded_perl`, `command_check_interval`, `p1_file`, etc.) and others became newly mandatory (`max_check_attempts` became required in v4, optional in v3), so in-place upgrades commonly break configs until manually patched ([Nagios Core Docs – Upgrading](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/upgrading.html); [Support Forum upgrade thread](https://support.nagios.com/forum/viewtopic.php?t=43037&start=10)).

## Security Model & Known Weaknesses

**NRPE trust model:** NRPE's core function — remotely triggering local command execution — has been a recurring source of vulnerabilities. Its own documentation warns that the `dont_blame_nrpe` option (letting the *poller* pass arguments to the remote check command) "should be considered a security risk, and should only be used if you know what you're doing." When enabled, insufficient sanitization of client-supplied arguments has repeatedly allowed command injection.

Documented CVEs:
- **CVE-2013-1362** (CVSS 7.5): incomplete blacklist in `nrpc.c` (NRPE < 2.14) allowed remote attackers to execute arbitrary shell commands via `$()` bash command-substitution metacharacters in check arguments.
- **CVE-2014-2913**: incomplete blacklist in `nrpe.c` (NRPE ≤ 2.15) allowed remote command execution via a newline character injected into the `-a` option to `check_nrpe`, bypassing the existing filter (disputed by the vendor as "expected behavior," since it only manifests with `dont_blame_nrpe=1` enabled) ([Arch Linux advisory](https://security.archlinux.org/CVE-2014-2913), [IBM security bulletin](https://www.ibm.com/support/pages/security-bulletin-vulnerability-nrpe-affects-powerkvm-cve-2014-2913)).
- **NRPE argument-processing risk** more broadly: Tenable/Nessus flags any NRPE install with command-argument passing enabled as a standing risk regardless of patch level ([Tenable 73757](https://www.tenable.com/plugins/nessus/73757), [Tenable 66361](https://www.tenable.com/plugins/nessus/66361)).

Nagios Core itself has its own CVE history, including: site-wide **CSRF** in Core 4.2.4 across state-changing functions (add/delete hosts, services); **XSS** in Core 4.4.2 via alert summary reports, demonstrable by a malicious `check_load` plugin output rendered unsanitized in the web UI; **NULL-pointer-dereference DoS** in the query-handler code (`qh_core`, `qh_echo`) affecting Core ≤ 4.4.1, triggerable via a crafted payload to the local Unix socket; and a **privilege-escalation** issue (Core ≤ 4.3.4) where the main `nagios` binary initially runs as root but supports configurations where it's owned by a non-root account, letting local users with access to that account escalate privileges ([CVE Details – Nagios Core](https://www.cvedetails.com/product/40171/Nagios-Nagios-Core.html?vendor_id=1424); official index at [Nagios Security Disclosures](https://www.nagios.com/security-disclosures/)).

**Encryption/auth posture more broadly:** classic Nagios deployments (especially pre-2015-era guides still widely circulated) commonly run NRPE and NSCA with plaintext or weakly-authenticated channels (a shared password for NSCA, SSL without certificate validation in many NRPE configs) rather than mutual TLS — something admins must deliberately opt into rather than get by default.

## Scaling & Operational Limitations

The most cited structural limitation is that **all checks in a single Nagios Core instance are scheduled by one central process on one machine** — there's no native clustering, sharding, or distributed scheduler. As one summary puts it: "The biggest problem with Nagios is the fact that all checks are scheduled on a single machine, which makes it not scale well" ([Nagios Support Forum discussion](https://support.nagios.com/forum/viewtopic.php?f=7&t=33245); background in [Nagios Core Docs – Distributed Monitoring](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/distributed.html)).

Reaching high check volumes (vendor materials cite "20,000+ service checks on a single host") requires deliberately engineered distributed setups — multiple independent Nagios instances federated together, or third-party schedulers like **mod_gearman** or the (now largely dead) **DNX** project — none native/default capabilities of Core; they're bolt-on architecture patterns the operator must design and maintain ([Distributed Monitoring Solutions for Nagios PDF](https://assets.nagios.com/downloads/general/docs/Distributed_Monitoring_Solutions.pdf)).

Other operational pain points: **polling overhead** (check density is bounded by CPU/process-table capacity on the central poller, since every check is a fork/exec, not just network I/O); **feature gaps filled only by addons** — visualization/topology maps (NagVis), GUI configuration (NConf), performance graphing (PNP4Nagios) are not native to Core, but separate community projects that must be installed, version-matched, and maintained alongside it, each with its own config format and lifecycle ([NagVis.org](https://www.nagvis.org/), [Nagios Add-on Projects](https://www.nagios.org/projects/nagios-core-addons/)); and **upgrade friction** — major-version upgrades routinely break existing configs due to deprecated/newly-mandatory directives, with no automated migration tooling.

## UI/UX Limitations

The stock Nagios Core web UI is widely described as dated and function-over-form: it renders host/service status largely as flat HTML tables, wasn't designed with modern dashboarding, drill-down visualization, or mobile use in mind, and offers no native configuration editing (see Configuration Model above). Community commentary is consistent: "If you're used to modern web applications, the Nagios UI feels like stepping back in time... 'functional' is about the kindest word for it" ([Fivenines – Nagios Still Works, But Do You Have Time for It?](https://fivenines.io/blog/fivenines-io-vs-nagios-which-monitoring-tool-is-right-for-you/)). This gap is exactly why the addon ecosystem exists (NagVis for topology views, third-party dashboards like Nagdash, Thruk as an alternate frontend) — the stock UI is treated by the community as a starting point to be replaced, not a finished product.

## Why People Leave Nagios

Recurring themes across vendor comparison posts, migration write-ups, and forum/HN discussion:

1. **Configuration burden outweighs the free license.** A commonly repeated framing: Nagios "was released in 1999 and was the default choice for monitoring for two decades because it was free, dependable, and had a plugin for everything," but "most engineering teams are migrating away from Nagios not just because it has stopped working for them, but because maintaining it has become a full-time job" ([Icinga – Nagios Alternatives blog](https://icinga.com/blog/nagios-alternatives/)).
2. **No auto-discovery / poor fit for dynamic infrastructure.** Nagios's fully manual object-declaration model doesn't fit containerized or autoscaling environments; Prometheus is cited as superior because "Prometheus uses Service Discovery to automatically find and monitor changing targets, making it far superior for containerised environments" ([SigNoz – Best Nagios Alternatives](https://signoz.io/comparisons/nagios-alternatives/)).
3. **Modern config/GUI expectations.** Zabbix is frequently cited for offering "web-based configuration (no text files), better visualisation, and distributed monitoring out of the box" — a direct contrast to Nagios's flat-file-plus-addon approach.
4. **Architecture-level rewrites beat incremental patching.** Icinga 2 is described not as a fork with cosmetic changes but as "a complete rewrite with a new core, new configuration language, and cluster capabilities," built to remove Nagios's single-scheduler bottleneck while retaining NRPE compatibility for organizations with existing check investments.
5. **Alert quality/false positives and metrics mismatch.** One migration account cites a team that "moved from Nagios to Prometheus mainly due to the configuration effort Nagios required and the many false positive alerts it generated" ([HN thread #19852194](https://news.ycombinator.com/item?id=19852194)). More broadly, Nagios is a status/alerting system (current state + notification), not a time-series store; teams needing trending and capacity planning outgrow it or bolt on an external TSDB.
6. **Flapping/escalation quirks causing alert confusion.** Flapping detection suppresses notifications during rapid state changes, but flapping notifications are excluded from the normal notification-count logic used for escalations — so escalation paths don't reliably trigger during flapping episodes, and there are documented cases of admins left unaware a service was still critical after flap-detection re-enabled mid-flap ([Nagios Core Docs – Flapping](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/flapping.html); [GitHub nagioscore issue #91](https://github.com/NagiosEnterprises/nagioscore/issues/91)).

**Summary for Trust's positioning:** the plugin-as-executable model was genuinely good and durable — worth keeping. Nearly everything people cite as a reason to leave clusters around three gaps: (a) manual, text-file, non-discoverable configuration; (b) a single-node polling architecture with no native clustering/HA; and (c) a security model (particularly around NRPE-style remote execution) that defaults to permissive/unencrypted unless the operator actively hardens it. A local-first successor has room to keep the "any script is a check" ergonomics while fixing discovery, distributed/HA scheduling, and secure-by-default remote execution.
