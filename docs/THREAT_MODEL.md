# Trust — Security Research Report: Learning from Nagios's Weaknesses

## 1. Nagios/NRPE Historical Weaknesses

Nagios and its ecosystem (NRPE, NSCA, Nagios XI) have a long history of vulnerabilities that trace back to a handful of recurring architectural decisions rather than isolated bugs.

**NRPE's arbitrary-argument execution model.** NRPE (Nagios Remote Plugin Executor) was designed to let the central server tell an agent "run check X with arguments Y," which is convenient but dangerous. CVE-2013-1362 was an incomplete-blacklist flaw in `nrpe.c` (pre-2.14) that let a remote, unauthenticated attacker execute arbitrary shell commands via `$()` command-substitution metacharacters processed by bash, when the `dont_blame_nrpe` option (which enables passing command-line arguments to plugins) was enabled ([Tenable](https://www.tenable.com/plugins/nessus/66361), [legalhackers.com](https://legalhackers.com/advisories/nagios-nrpe.html)). A follow-up flaw, CVE-2014-2913, showed the sanitization was still incomplete: NRPE checked for shell substitution characters but not newline (`0x0A`), which bash treats as a command separator — so an attacker could smuggle a second command past the filter ([exploit-db](https://www.exploit-db.com/exploits/32925)). The deeper lesson isn't "the blacklist had a bug," it's that **blacklist-based sanitization of shell metacharacters is inherently fragile**, and any design that hands remote, semi-trusted input to a shell for argument interpolation will keep reproducing this bug class in new forms.

**NSCA's trust and crypto assumptions.** NSCA (Nagios Service Check Acceptor) is a passive-check mechanism where remote hosts push results to the server. Its own security documentation is candid that it depends on "reasonably secure" shared-password encryption and that any compromise of a "blessed" client machine (or its config file, which stores the password in plaintext) undermines the whole model; it explicitly warns that a malicious actor could submit fake check results to trigger false alerts or make event handlers take destructive action ([NSCA SECURITY.md](https://github.com/NagiosEnterprises/nsca/blob/master/SECURITY.md)). Because NSCA never had a proper certificate-based identity system, there's no clean way to revoke a single compromised client without rotating a shared secret used by everyone.

**Check plugins as injection vectors.** Nagios's plugin model treats "run a program with untrusted-adjacent arguments" as the norm, and this keeps resurfacing. `check_by_ssh` (CVE-2023-37154) passes user-influenced values into SSH's `-o` option parser; an attacker who controls those values can inject `ProxyCommand`/`LocalCommand`-style SSH options and pivot from "controls the monitoring server" to "gets code execution on every monitored host reachable over the wrapper-restricted SSH key" ([Joshua Rogers' writeup](https://joshua.hu/nagios-hacking-cve-2023-37154)). Nagios XI's web layer compounds this: authenticated OS command injection in the ConfigWizards feature (CVE-2021-25296/25297/25298), command injection during plugin upload, and a chained RCE via Core Config Manager's "Run Check" feature all stem from building shell command lines out of user-supplied configuration fields ([Rapid7](https://www.rapid7.com/db/modules/exploit/linux/http/nagios_xi_configwizards_authenticated_rce/), [CVE Details](https://www.cvedetails.com/vulnerability-list/vendor_id-1424/product_id-26507/Nagios-Nagios-Xi.html)).

**Weak/absent default web-UI security.** Classic Nagios Core relies on Apache Basic Auth against an `htpasswd` file that many self-hosters disable or never configure, especially on "private" LANs — a decision the official docs explicitly warn against ([Nagios CGI auth docs](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/cgiauth.html)). Nagios XI's commercial web app has accumulated an extensive CVE history of SQL injection (CVE-2018-8733, CVE-2023-40931/40933/40934) and authentication bypass in its Core Config Manager, several of which chain unauthenticated SQLi into full admin takeover ([rootsecdev](https://rootsecdev.medium.com/notes-from-the-field-exploiting-nagios-xi-sql-injection-cve-2023-40931-9d5dd6563f8c), [CVE Details](https://www.cvedetails.com/cve/CVE-2018-8733/)). NCC Group also found NRDP/NSCA authentication tokens stored in plaintext (CVE-2023-47402) ([NCC Group advisory](https://www.nccgroup.com/research/technical-advisory-multiple-vulnerabilities-in-nagios-xi/)).

**Stored/reflected XSS from host-supplied data.** GRIMM's research showed that Nagios renders external-command fields (e.g. comment text attached to a host) and NCPA agent responses without sanitization, so a compromised passive-check client or agent can inject a payload that executes in an administrator's browser session — and from there create new admin users or reach plugin-upload RCE, eventually escalating to root via privileged helper scripts ([GRIMM Cyber](https://grimmcyber.com/escalating-xss-to-sainthood-with-nagios/)). This is the clearest illustration in the whole Nagios CVE history of why "data that originates from a monitored host" must be treated as untrusted input in the UI, not just at the network boundary.

## 2. Secure Agent/Check Execution Design Patterns

- **No shell interpolation, ever.** Checks should be invoked via `execve`-style APIs (`ProcessBuilder`, `execFile`/`spawn`, Go's `exec.Command`) that pass arguments as an array, never through `/bin/sh -c "..."` string concatenation — this structurally removes the metacharacter class of bug that caused CVE-2013-1362/2014-2913 ([OWASP OS Command Injection Defense Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)).
- **Signed/allow-listed check definitions instead of arbitrary remote command execution.** The server should not be able to tell an agent "run this arbitrary program with these arguments." Instead, the agent ships with (or pulls, signed) a fixed catalog of check definitions with a strict argument schema (typed, bounded, regex-validated), and the server can only select from and parameterize within that schema — never inject raw command strings or new executables.
- **Least-privilege execution.** Checks run as a dedicated unprivileged user, ideally with OS-level sandboxing (systemd `ProtectSystem=strict`, `NoNewPrivileges`, seccomp filters, or a container/namespace per check) so that even a successful injection inside one check plugin can't read other checks' credentials or touch the host.
- **Mutual TLS between server and agents**, with per-agent certificates (not a single shared PSK) so a compromised agent can be individually revoked. Zabbix's TLS-with-certificate mode and Checkmk's registration-issued per-host secret are concrete precedents ([Zabbix encryption docs](https://www.zabbix.com/documentation/current/en/manual/encryption), [Checkmk security docs](https://docs.checkmk.com/latest/en/security.html)).
- **Explicit, authenticated agent registration**, not "first request wins." Checkmk's `cmk-agent-ctl register` model — a one-time enrollment step that establishes a host-specific secret before any check traffic is trusted — is a strong pattern because it avoids the "anyone on the LAN who speaks the protocol becomes a trusted agent" failure mode that plain auto-registration (Zabbix's older default) has been criticized for ([Zabbix auto-registration docs](https://www.zabbix.com/documentation/current/en/manual/discovery/auto_registration)).
- **Never trust push-model results without cryptographic identity.** NSCA's password-encrypted, non-revocable-per-client model shows the failure mode; per-agent certs plus a nonce/timestamp in each result (to prevent replay) are the fix.
- **Centralized secrets, scoped per check.** SNMP community strings, SSH keys, WMI/DB credentials should live in an encrypted secrets store on the server (or a local OS keyring on the agent) that individual check processes only receive at invocation time, scoped to that single check, never written to plaintext config files or command-line arguments (which are visible via `ps`) ([OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)).

## 3. Control-Plane (Web UI) Security Considerations

- **Auth model:** local accounts with strong password hashing (Argon2id) plus optional OIDC/SSO for organizations that already run an identity provider. Local authentication remains necessary for isolated deployments and recovery access.
- **Session security:** short-lived, rotating session tokens, `HttpOnly`/`Secure`/`SameSite=Strict` cookies, and CSRF tokens on all state-changing requests — Nagios XI's history of CCM authentication bypass shows what happens when config-changing endpoints are reachable without a real session check ([CVE-2018-8733](https://www.cvedetails.com/cve/CVE-2018-8733/)).
- **RBAC for multi-user setups:** read-only viewer, operator (ack/silence), and admin (config/credentials) roles at minimum, since a monitoring dashboard often becomes a de facto inventory of the whole network and shouldn't be all-or-nothing.
- **Treat all host-supplied data as untrusted in the UI.** Hostnames, check output, and comment fields must be HTML-escaped/context-encoded on render — GRIMM's XSS-to-root chain in Nagios is a direct result of not doing this ([GRIMM Cyber](https://grimmcyber.com/escalating-xss-to-sainthood-with-nagios/)).
- **Internet exposure:** ship secure defaults (auth enabled out of the box, no default credentials) and documentation steering users toward a reverse proxy / VPN rather than direct port-forwarding, since dashboards forwarded to the internet without hardening are routinely found by mass scanners like Shodan ([Shodan Internet Exposure Dashboard](https://exposure.shodan.io/)).
- **SQL injection prevention:** parameterized queries/ORM everywhere — Nagios XI's repeated SQLi CVEs (CVE-2023-40931/40933/40934) came from string-built SQL in admin-facing AJAX helpers ([rootsecdev](https://rootsecdev.medium.com/notes-from-the-field-exploiting-nagios-xi-sql-injection-cve-2023-40931-9d5dd6563f8c)).

## 4. LAN Threat Model Considerations

Even though Trust targets private networks, "on a LAN" is not a trust boundary. Professional environments can contain guest networks, unmanaged devices, or a compromised endpoint that gives an attacker internal network access. Design for an attacker who is *already inside*:

- **Agent impersonation / rogue registration:** without per-agent identity, any host on the LAN speaking the agent protocol could register as a monitored device or, worse, as the "server" and harvest credentials pushed to agents. Explicit enrollment (an admin-approved registration token, as in Checkmk) closes this, versus Zabbix's historically looser auto-registration ([Zabbix auto-registration docs](https://www.zabbix.com/documentation/current/en/manual/discovery/auto_registration)).
- **MITM between server and agents:** mandatory TLS with certificate pinning/CA validation (not opportunistic/optional TLS as in Prometheus's ecosystem by default) prevents ARP-spoofing-based interception ([Prometheus security model](https://prometheus.io/docs/operating/security/)).
- **DNS/ARP spoofing affecting discovery:** any network-discovery feature (auto-detecting hosts to monitor) must not auto-trust discovered hosts; discovery should only populate a review queue for an admin to approve, never auto-enroll.
- **Comparable tools' precedent:** Zabbix supports PSK/cert TLS but ships unencrypted-by-default; Checkmk enforces "registered host refuses unencrypted connections" once TLS is turned on; Prometheus's node_exporter has essentially no built-in auth and explicitly documents that operators must add TLS/mTLS or a reverse proxy themselves ([o11y.eu](https://o11y.eu/blog/prometheus-tls/), [Checkmk docs](https://docs.checkmk.com/latest/en/security.html)). Trust should default to authenticated and encrypted communication so a secure baseline does not depend on post-installation hardening.

## 5. STRIDE-Style Threat Checklist

| Threat Category | Example Attack | Mitigation Pattern |
|---|---|---|
| **Spoofing** | Rogue host on the LAN registers itself as a monitoring agent or impersonates the server to harvest agent credentials | Mutual TLS with per-agent certs issued via admin-approved enrollment token; no implicit trust-on-first-connect |
| **Tampering** | Attacker on-path modifies check results in transit (e.g., suppress a "disk full" alert) or rewrites check definitions pushed to an agent | TLS with integrity (AEAD ciphers), signed check-definition bundles, config file integrity hashing |
| **Repudiation** | Admin or compromised account silences alerts / deletes hosts with no trace | Immutable, append-only audit log of all config changes and ack/silence actions, tied to authenticated identity |
| **Information Disclosure** | SNMP community string, SSH key, or DB credential leaked via plaintext config file, command-line args (visible via `ps`), or verbose error page | Central encrypted secrets store, credentials injected at check runtime only, generic error messages to UI |
| **Denial of Service** | Flood of fake passive check submissions or a runaway check plugin exhausts agent/server resources | Rate limiting per agent identity, resource/time limits (cgroups) per check execution, backpressure on ingest queue |
| **Elevation of Privilege** | Command injection in a check plugin argument, or XSS in the dashboard escalating to admin account creation | Array-based process execution (no shell), strict argument schemas, output-context encoding of all host-supplied data in the UI, least-privilege check execution sandboxing |
